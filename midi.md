# What this synthesiser does with MIDI

`README.md` says what this is, `sources.md` where the physics came from,
`coverage.md` how faithful each of the 128 programs is. This file is the
control surface: every message the engine answers, what it does, and which of
the two renderers answers it.

THE SPLIT IS REAL AND THIS DOCUMENT EXISTS BECAUSE OF IT. `live.py` is an
engine with a keyboard attached; `blockrender.py` reads a finished file and can
therefore see the whole of it before it renders a sample. Some messages only
make sense to one of them. A pedal makes sense to both, and for a while made
sense only to one.

It also exists because of a specific failure. `blockrender.py`'s own docstring
once listed three things the renderer did not do, all three were implemented,
and the list stayed — so a later reader, finding a difference in a measurement,
had a ready-made and entirely wrong explanation for it. The docstring says so
itself: *"The list outlived the omissions, which is worse than no list."* Four
lines below that warning the same docstring then claimed every partial runs at
a constant frequency, which the pitch-bend glide had already stopped being
true. An undocumented feature costs you the feature. A wrongly documented one
costs you the measurement.

## Every message, and who answers it

Generated by reading the dispatch in both files — `msg.control ==` in
`live.py`, the `cc ==` filters in `blockrender.py` — rather than transcribed,
for the reason above.

| message | live | file | what it does |
|---|---|---|---|
| note on / off | ✓ | ✓ | velocity is loudness, and on a struck voice also timbre |
| program change | ✓ | ✓ | all 128 GM programs; channel 10 is percussion |
| pitch wheel | ✓ | ✓ | a temperament when static, a gesture when it moves — see below |
| channel aftertouch | ✓ | ✓ | crescendo: **+8 dB** and brighter together (`PRESS_DB`, `PRESS_TILT`) |
| polyphonic aftertouch | ✓ | ✓ | the same, per note |
| SysEx | ✓ | ✓ | GM System On, and GM2 Scale/Octave Tuning in both byte forms |
| CC1 modulation | ✓ | ✓ | seven controls live, five in a file, chosen by voice — see below |
| CC5 portamento time | ✓ | ✓ | the glide's **rate**, not its duration |
| CC6 / CC38 data entry | ✓ | | into the selected RPN |
| CC7 volume | ✓ | ✓ | channel fader, default **100** |
| CC10 pan | ✓ | ✓ | a position, not a fader |
| CC11 expression | ✓ | ✓ | the second fader, default **127** |
| CC64 sustain | ✓ | ✓ | damper off, on voices that have one |
| CC65 portamento | ✓ | ✓ | the switch; the next note glides from the last |
| CC66 sostenuto | ✓ | ✓ | holds only what was already down |
| CC67 soft | ✓ | ✓ | una corda: a string count, not a filter |
| CC84 portamento control | ✓ | ✓ | its byte is a **source note number**; fires once |
| CC91 reverb send | | ✓ | distance from the microphone |

| CC98 / CC99 NRPN | ✓ | | selected and then deliberately ignored |
| CC100 / CC101 RPN | ✓ | | selects 0/0, 0/1, 0/2 |
| CC120 all sound off | ✓ | ✓ | the panic — stops the channel dead, pedal or no pedal |
| CC121 reset controllers | ✓ | | re-sends CC1/11/64/66/67 at their defaults |
| CC123 all notes off | ✓ | | lifts the keys; the pedal still holds them |

Twenty controllers live, thirteen in files. Three RPNs: **0/0** bend range,
**0/1** fine tuning (14-bit, ±100 cents), **0/2** coarse tuning (MSB only,
±64 semitones). NRPNs are selected so that a file which sends one does not have
its data entry land in whatever RPN was selected last — the select is honoured
precisely in order to discard what follows it.

CC120 against CC123 is not pedantry and cost a commit to get right. **CC120 is
the panic**: it stops sound regardless of the damper. CC123 lifts the keys, and
a note under a held pedal keeps ringing, which is what the pedal is for. A
panic button that sends CC123 into a pedalled passage does nothing audible.

## A tuning is not a gesture

The pitch wheel is two unrelated controls sharing a byte pair, and the
difference is whether it moves.

A bend set before a channel's first note and never touched is a TEMPERAMENT. It
belongs in `f0`, every voice takes it, and a voice with no way to bend a
sounding note takes it anyway — a harpsichord is tuned before the recital like
everything else. Sankey's corpus is the worked example: his files set a wheel
offset per channel to get his temperament out of an equal-tempered synthesiser,
and `bwv847.mid` asks for twelve of them. Measured against the table it asks
for: **0.00 cents** of error on every one.

A bend that moves during a note is a GESTURE, and most instruments cannot make
one. That is `pitch_bendable`, and it is false on nine classes, which between
them are everything with no way to alter a pitch already sounding: the
harpsichord and the grand piano, the Rhodes and the Wurlitzer, the tonewheel
organ, the flue organ ranks, the free reeds, the tuned bars, and the bagpipe —
whose chanter's finger holes are drilled where they are drilled.

It was briefly false on the whole organ class, which took the trumpet, the
clarinet and the shanai down with it. A reed pipe is an organ stop by cabinet
and a wind instrument by physics, and a player bends those, so the property
belongs on `FlueOrganProperties` and not on the base.

The moving case is where the file renderer stops holding partials at a constant
frequency. `bend_blocks` gives the kernel two extra rows per channel and the
phasor integrates through them. The trick that keeps it to two rows rather than
two per partial: a bend is a RATIO, so the phase a partial accumulates over a
block is `w·(r−1)·BLK` and the partial's own frequency `w` factors straight
out. The cumulative term is partial-independent. The kernel stays stateless.

## A glide is a length moving, not a pitch moving

Three controllers, and they are not three settings of one thing. CC65 is a
switch, CC5 is a speed, and CC84 is neither.

**Roland is the primary source and it settles two of the three.** The SC-55
manual is a scan with no text layer (`sources.md`), but the **VE-GS Pro MIDI
Implementation** is the same GS control set with the text intact:

- CC5 *"adjusts the **rate** of pitch change … A value of 0 results in the
  fastest change"*, initial value 0. **Rate, not time** — so a wide glide takes
  proportionally longer than a narrow one.
- CC65 is *"0-63 = OFF, 64-127 = ON"*, the same switch point the three pedals
  collapse half-pedalling at.
- CC84's data byte is a **source note number**. It arms the next note-on to
  start from that pitch, once, and it does not need CC65 — Roland's Example 2
  sends it with nothing sounding at all and the note still glides.

What Roland does **not** publish is the curve from CC5's byte to a real speed.
That is chosen in `tonelib.porta_semitone_time` and is anchored on a semitone:
**2 ms at CC5 = 0** (which is to say, not a glide at all, because that is what
"fastest" has to mean) to **300 ms at CC5 = 127**, geometric between.

### What actually moves is a length

A trombone slide, a finger on a string and a slide whistle's plunger all change
a LENGTH, and `f = k/L`. So the distance in a glide is `|1/f_src − 1/f_tgt|`,
and the kernel's frequency factor is a **reciprocal** settle rather than the
exponential the tension bend uses:

    bendfac = 1 / (1 + g·e^(−t/τ))        g = f_target/f_source − 1

Two things fall out that nobody put in:

| | |
|---|---|
| **direction** | the same interval takes the same time either way — it is the same travel |
| **register** | the same interval takes **4× longer two octaves down**: a semitone in the pedal register is far more slide than a semitone at the top |

An earlier draft normalised the travel by the *target* length instead, which
made a glide up 25% slower than the identical glide down. That is an artefact
of a normalisation, and the only thing worse than not having a physical claim
is having to defend one you did not mean to make.

### Up and down are not mirror images

They take the same time; they do not take the same path. As the tube shortens
the same remaining travel is worth more cents, so an upward glide **lingers**
near its target and a downward one **arrives sooner**. Measured as the time to
cover half the interval in cents, in units of τ:

| | |
|---|---|
| up, C4 → E4 | **0.749 τ** |
| a lag circuit | 0.693 τ (ln 2) |
| down, E4 → C4 | **0.607 τ** |

The circuit sits exactly between them, which is what it means for an arm and a
capacitor to settle in different coordinates.

### What each voice glides with

`pitch_bendable` is the wrong gate: a trumpet is bendable and still cannot lip
a glide of a fifth. So the property is a mechanism, not a flag.

| `glide_mechanism` | programs | reach | what it is |
|---|---|---|---|
| `slide` | 2 | 6 st | a trombone's seven positions, one continuous slide |
| `stop` | 12 | 7 st, 12 st | the violin family at a hand position; a fretless bass neck is longer |
| `valve` | 4 | 2 st | trumpet, horn, tuba — **see below** |
| `circuit` | 31 | unbounded | the synthesisers, settling in pitch rather than length |
| *(none)* | 79 | — | piano, organ, harpsichord, mallets, bagpipe, free reeds |

A voice with no mechanism ignores all three controllers, and its partial table
is **bit-identical** with and without them.

### The valve case is not a longer slide

Ben, who plays these:

> When we brass players glissando, we do it in many ways. 1. move cleanly from
> one fingering to another, and blow through the harmonics. 2. move arbitrarily
> the valves while blowing through the harmonics. 3. pressing down half way on
> one of the valves to interfere with harmonic alignment, while muffling the
> gliss, in between. 4. backing off the mouthpiece for a similar effect, to
> allow for more lip sway.

So a valved gliss walks a LATTICE — harmonic *n* over whatever length the
valves have added — and `brass_fingering.py` already knew that lattice, having
been written for intonation.

**The file renderer therefore emits a run of real notes**, which is not a
workaround: the model says a run of pitches is what is happening, so a run of
pitches is what gets built. Each step goes through the same note loop as
everything else and so picks up its **fingered** pitch for free. Measured on a
C4 → G4 rip:

    91.7  111.2   91.6   91.9  112.3   91.7  111.6      cents per step

An equal semitone is 100.0 throughout. That **20.7 cents of spread** is where
the valves actually put those notes, and it is a good part of what makes the
gesture sound like a player rather than a pitch ramp.

The run is **even, not exponential**. The reciprocal settle is a hand
decelerating into a target, which is what a slide does; ripping through seven
fingerings is a sequence of discrete actions at a steady rate — and an
exponential would never reach the last step.

**CC5 opens the smear, and Ben's suggestion is why.** A quick gliss is a rip
and the steps are the sound of it; a slow one is held, and a player holding a
staircase half-valves instead. So each rung arrives *from* the one below with a
τ that opens with CC5, and the level comes down with it:

| | τ into each rung | level through the middle |
|---|---|---|
| CC5 = 20 | 3.7 ms — clean steps | **−0.2 dB** |
| CC5 = 110 | 92.8 ms against a 143 ms step | **−2.6 dB** |
| trombone, either | no lattice at all | +0.0 dB |

The dip is the tell: half-valving breaks the harmonic alignment and loses
support. Without it a smear is just a portamento wearing a staircase.

**Live does not do this.** Those note-groups have to be scheduled ahead on the
audio thread and nothing there does that yet, so live glides a valved voice
only as far as the lip reaches — about a tone, technique 4, which is real — and
plays anything wider clean. The two paths agree up to two semitones and diverge
deliberately past it.

### Where the two renderers meet

The file path can see the whole file, so it decides every note's source pitch
in one pass before rendering a sample. Live cannot: it keeps the last note-on
per channel, because `self.down` is a **set** and knows what is held without
knowing what went down last.

Both then write the same three floats per partial — `gb`, `gt`, `gc` — and one
piece of C renders them, so the two agree by construction rather than by
calibration. Measured, they differ by **exactly zero**.

One deviation to record. Roland says that if a voice is already sounding at
CC84's source note, *"this voice will continue sounding (i.e., legato)"* and
becomes the new note — so the source note's later note-off does nothing. Here
the bank's template cache is keyed on the note, so a fresh voice starts with
the glide stamped and the old one is released. The audible difference is one
attack transient, which is what `legato_attack_s` exists to suppress.

## Pan is a position, not a fader

CC10 places the source in the room and the head does the rest. Both ears get
the sound; what differs is when and how much.

| | hard left, at the right ear |
|---|---|
| 100 Hz | **0.10 dB** down — the head is not in the way of a 3.4 m wave |
| above 3 kHz | **15.2 dB** down — the head is a wall |
| arrival | **0.505 ms** late (0.518 hard right) |

An amplitude pan would be flat across frequency and simultaneous at both ears.
It would also be a different effect, and the reason a mix panned that way
collapses to the middle of the head rather than spreading across the room.

## A send is a mix, not an addition

A send that adds a wet copy to an untouched dry signal is a volume control with
extra steps: turn it up and the channel gets louder, which is not what anyone
reaches for a send to do. CC93 and CC91 both avoid that, and they avoid it
differently, because they are sending to different places.

**CC93 takes the wet share out of the dry one**, in POWER rather than
amplitude, because the detuned copies are incoherent with the original and
incoherent sources add as powers:

    wet = (send / n_copies) ** 0.5
    dry = (1 - send) ** 0.5

Measured at full send: **+0.00 dB**. The level does not move; only the width
does.

**CC91 scales the room feed and leaves the dry alone.** That looks like the
mistake above and is not, because the thing being controlled is a RATIO.
Reverberant-to-direct is what a distance actually sets; the absolute level is a
normalisation, and holding the direct sound fixed is the normalisation that
makes the control behave like a send instead of a fader. It also falls out of
the room equation rather than being imposed on it: the impulse response's SHAPE
does not depend on r and only its amplitude does, so a whole channel's
contribution to the tail is one scalar. That is a textbook send bus, arrived at
from Sabine.

The test that catches the other version of either: render with the send at zero
and with it absent. The dry mix must be **bit-identical**. It is.

Summing `|amplitude|` where incoherent sources are involved is the same mistake
one level up, and it was made here — on a measurement, not in the renderer —
reporting **+3 dB** on a mix that was level-neutral.

## Chorus is a fixed detuning, and that is why it can be a post-pass

CC93 adds detuned copies at **±7 cents**, swept slowly, floor at 0.02.

This works as a post-pass over the partial table for a reason that is a fact
about instruments rather than about the code. A piano's unisons are DRAWN: the
three strings of each note are mistuned by amounts particular to that note, and
`pl` stamps each copy so they can be. But an accordion's musette, a string
machine's chorus and a synth brass ensemble are all FIXED offsets — the same
cents at every note, by construction, because that is what the hardware does.
`tonelib` states it three times, at the accordion, the string machine and the
synth brass, because it is three times load-bearing. A fixed offset can be
applied to a table of partials after the fact. A drawn one cannot.

## Reverb is distance, and the bass reaches the room first

CC91 is a distance from the microphone, against one shared room. Sabine gives
the decay and the room constant:

    t60   = 0.161·V / (−S·ln(1−α) + 4mV)
    R     = S·α / (1−α)
    ratio = 16πr² / (Q·R)

**T60 contains no `r`.** The room rings for as long as it rings wherever you
stand; only the ratio of reverberant to direct energy has the distance in it,
and it has it as r². So moving the microphone does not change the decay, it
changes the mix — which is exactly what a send control ought to do, and is the
whole reason the control can be a distance at all.

| | T60 | critical distance |
|---|---|---|
| 63 Hz | 2.08 s | **6.06 m** |
| 1 kHz | 1.33 s | **7.79 m** |
| 16 kHz | 0.58 s | 7.49 m |

Critical distance is where reverberant energy equals direct. It is nearer at
63 Hz than at 1 kHz, so as you walk away from a source the BASS goes to the
room first and the room gets warmer as it gets further. Nobody tuned that in;
it falls out of α rising with frequency.

CC91 is file-only. Doing it live is new DSP on the audio thread — a partitioned
convolver or an FDN — not a port of anything.

## Una corda is a string count

CC67 on a grand shifts the action so the hammer reaches two strings instead of
three. It is therefore a build-time fact about how the note was struck, read at
the ONSET: once a note is sounding, moving the pedal cannot un-strike a string.

| | offline | live |
|---|---|---|
| C4 | **−1.09 dB** | **−1.20 dB** |
| C2 | unchanged | unchanged |

C2 is unchanged because a bass note has one wound string and there is nothing
to drop. This is what makes it a string count and not a filter: a filter would
have taken something off C2 as well, and it would have been the same something
at every pitch.

Live took the wrong string for a while — "the highest string present" was
implemented as "the second one", which in the bass is a different string
entirely, and the two paths diverged by 0.48 dB. The instrument has to be asked
which index that is, because `note_detune_cents` is per note.

## Sostenuto is not sustain with a different number

CC66 catches only the keys that were already down when it went down, and lets
everything played afterwards damp normally. That asymmetry IS the instrument,
and nothing else in the renderer expresses it: the damper answers "is the pedal
down", the phrase detector answers "is the channel active", and neither answers
"what was sounding at this instant". It is keyed on the note instance —
`(channel, note, onset)` — because being caught by the pedal is a fact about
one press of one key.

Both pedals collapse half-pedalling at 64, which is where GM puts the switch.
Half-pedalling is real in the corpus: Sankey's `ondine.mid` writes
0/24/40/56/72/88/104/127 on CC64. Anything under 64 is the damper on the
string.

## CC1 is seven controls, chosen by voice

The mod wheel is whatever the instrument's most-moved control is, and asking
which that is per PART rather than per channel matters, because a layered
channel can be two of them at once:

| voice | the wheel is | live | file |
|---|---|---|---|
| most | vibrato — **35 cents** deeper and 25% faster at full | ✓ | |
| flue organ | the crescendo pedal, drawing stops 8′ 4′ 2′ 2⅔ 16′ 5⅓ | ✓ | |
| Rhodes, Wurlitzer | the tremolo depth — a tine cannot be bent anyway | ✓ | |
| amplified | the gain knob — a guitar amp's drive, a Leslie's swell | ✓ | ✓ |
| clavinet | the tone rockers, sweeping dark to bright | ✓ | ✓ |
| honky-tonk | the detuning between the two strings | ✓ | ✓ |
| bagpipe | how many drones are on: **0 is the chanter alone** | ✓ | ✓ |
| Leslie | the half-moon switch: stop → chorale → tremolo | | ✓ |

The three the file renderer leaves alone are the three that are GESTURES —
vibrato, a crescendo, a tremolo swell are things a hand does while playing,
and a file that wants them writes them as notes and expression. The four it
keeps are SETTINGS, and it reads each from the channel's first CC1 and holds
it: a player sets the rockers, corks the drones, and then plays.

The Leslie row is the one asymmetry, and it is deliberate. Offline CC1 is the
half-moon switch; live it is the swell pedal, and the half-moon moved to the
pitch wheel — because a half-moon is read as an EDGE and what makes a flick
work is the spring return, which a written bend has no reason to have. A
Hammond has neither wheel to spare, which is what made both moves possible.

The bagpipe is the one that is a channel setting rather than a gesture. A
piper does not switch drones mid-tune; they are corked before the tune starts.
So the wheel is read once per channel, before any note is built.

That last clause is the correction. The drone count was first written in the
per-channel block, which runs AFTER every note has been built — so the wheel
did nothing and every value gave three drones. The honky-tonk's wheel had gone
inert in exactly that way, the fact was recorded in `sources.md`, and it was
reintroduced within the hour by someone who had read it.

## What a voice can refuse

A controller is not a property of the protocol, it is a question put to an
instrument, and instruments decline. Four properties carry the declining:

| property | false means |
|---|---|
| `damper_pedal` | CC64 does nothing — an organ has no dampers to lift |
| `pitch_bendable` | a moving wheel does nothing; a static one still tunes it |
| `touch_sensitive` | velocity does not set level; CC7 and CC11 still do |
| `soft_pedal_strings` | 0 strings to drop, so CC67 does nothing |

`touch_sensitive` is the subtle one, and Ben's question is the clarifying one:
*"Do patches that are fixed volume still adjust with channel volume? Just
attack volume is fixed?"* Yes, and yes. A pipe organ key is a valve — it is
open or shut, and how fast you pushed it changes nothing — but the swell
shutters and the stops are still controls. The bagpipe is the same: the bag is
at the pressure the piper's arm holds, the chanter has no dynamics at all, and
the channel fader is the only level there is.

## Tuning by SysEx

GM2 Scale/Octave Tuning, both byte forms, one offset per pitch class applied
across the whole compass.

| form | worst error over a 12-note table |
|---|---|
| 2-byte | **0.005 cents** |
| 1-byte | **0.290 cents** |

0.290 is not a bug; the 1-byte form quantises to whole cents and that is its
resolution. The table is idempotent — sending it twice moves nothing — and a
GM System On clears it.

Eleven of this renderer's twenty tuners are exactly a Scale/Octave table and
survive the round trip unchanged: `bechstein`, `even`, `hybridharm`,
`hybridharm440`, `just`, `linear`, `linear5`, `linearwell`, `meantone`, `pyth`,
`well`. The rest are not, and the reason is interesting: they STRETCH. A tuner
that spreads 237.86 cents across the compass (`dynamic`) or 20.51 (`path`) is
saying something an octave-repeating table cannot say, and a SysEx export of it
can only be an approximation taken at C4. Even `werckmeister` and `sankey`
spread 0.36 cents, because their octaves are stretched a little. A temperament
fits in this message. A stretched piano does not.

## Three corrections that are worth the space

**`sweep` steals anything whose key is not down.** The voice allocator's
scavenge pass looks for voices with no key holding them and takes them, which
is correct and is how you get polyphony back. It is also how the amplifier lost
its tail, how the bagpipe's drones went silent, and how sostenuto's caught
notes were released — three separate features, all in one session, all
presenting as a different bug each time. Any feature that holds a voice without
a key down has to say so, or `sweep` will be right about it and wrong for it.

**The amplifier backed out the wrong gain.** The solver normalised with
`sc = sqrt(power/have)/unit`, which divides out the unit but not the stage gain
`g` — between 2.52 and 2.98. So every amped voice arrived at the valve curve
that much hot and distorted **8.0 to 9.4 dB** harder than asked. The symptom
was that the distortion controls felt wrong, not that anything was silent, and
that is what made it live for as long as it did.

**A comment stated the intent while the code did the opposite.** `pickup_gain`
divided by the coil count, directly beneath a comment reading *"Summed, not
averaged"* — **−6.02 dB** on every humbucker in the instrument. The comment was
right about what should happen. It had been right for long enough that it read
as a description of the code rather than a claim about it, which is the failure
mode that makes a wrong comment worse than no comment.

All three are the same shape as the docstring at the top of this file, and are
the reason this file is generated from the dispatch rather than typed out.
